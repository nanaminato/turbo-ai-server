# 角色与功能权限

角色授权现在使用不可变的 Code；Name 为可修改的显示名称，Description 为说明。角色响应包含 isSystem 和 memberCount（去重账户数）。新编码为 2–64 位小写字母、数字、下划线、短横线，字母开头；旧角色迁移保留 Name 原值作为 Code，因此旧功能权限 JSON 的键不变。

admin/user/vip 是系统编码，不能删除或改编码，可以修改名称和说明。所有角色编码创建后不可修改。自定义角色删除会在同一事务中清除其功能授权并推进策略 revision；重新创建相同编码不会恢复旧授权，旧页面保存会发生冲突。多角色功能合并仍采用任一角色允许即允许，各限额取最宽值，任一无限额则该项无限额。

账户新增、编辑、删除和角色删除使用事务。账户角色引用必须存在且不重复。MySQL 对 admin 角色行加 FOR UPDATE 锁，串行化各实例的成员变更；检查与写入在同一事务中，拒绝移除最后一个管理员。存在其他管理员时允许删除管理员账户。权限变更及账户删除在提交前撤销会话，失败则数据库事务回滚。缓存可能先失效导致重新登录，但不会保留被撤销权限。

角色目录仅管理员可读；账户自身可按自己的 userId 查询角色，其他账户分配仅管理员可读。功能策略保存也持有同一角色锁并在事务内重查角色编码，避免删除后旧编辑器重新引入授权。

## 已有数据库部署

正常启动只读检查要求 Roles.Code、Roles.Description、Code 唯一索引以及 AccountRoles(AccountId,RoleId) 唯一索引。已有库须停止应用写入后执行 src/RelaxKon.Auth/Resources/merge/role-system-upgrade.sql，再启动新版后端。新库 init.sql、open-initdata.sql 和 create-admin 脚本已同步。角色迁移不修改聊天历史或功能策略内容。

升级脚本为一次性 MySQL DDL，会隐式提交，不能依赖事务整体回滚。先核对/备份数据库。脚本先用临时 CHECK 表拒绝空名称、超过 64 字符、重复角色名、重复成员绑定；需人工修复这些既有异常后再迁移，禁止自动合并权限。部署客户端须遇错停止，不能使用 mysql --force 跳过保护。中断后先检查实际列和索引，禁止整份盲目重跑。运行中的旧后端仍按 Name 授权，因此不能混用新旧后端并修改显示名。

2026-11-05 已完成开发业务库 `niko` 的角色结构升级。升级前确认本机无运行中的后端、目标库无其他应用连接，保存角色及成员绑定快照后执行迁移。3 个角色和 3 条绑定完整保留，全部 22 张业务表行数不变，功能权限策略内容哈希与版本未变化。新版 Release 后端通过启动结构检查，角色及功能权限接口的未登录请求均返回 401。验证实例已关闭，恢复原先的停止状态。迁移快照与核对结果位于被 Git 忽略的 `TestResults/role-upgrade-20261105-230343/`。

## 审计与错误

现有结构化日志记录角色创建/编辑/删除的操作者、目标、编码及名称变化；账户变更记录操作者、目标和变更前后的角色编码，不记录密码或密钥。日志持久性由部署的日志输出和保留策略决定，本次未新增审计表或审计查询页面。

API 错误返回 code：last_admin_required、system_role_protected、role_code_immutable、role_already_exists、invalid_role_assignment、invalid_role、role_not_found、account_not_found、account_already_exists。角色不存在返回 404，重名返回 409，其余规则拒绝为 400。
