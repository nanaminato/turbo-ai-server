# 启动失败：架构迁移缺失

处理日期：2026-11-04。

## 原因

使用当前本地开发配置启动时，RoutingRefreshService 在接受 HTTP 流量前加载路由，查询 RoutingConfiguration 失败。实际数据库仍缺少 architecture-upgrade.sql 中的同步表、唯一索引和路由触发器；这是已发布代码与旧数据库结构不匹配，和官方 AI SDK 的初始化无关。

## 已完成的开发环境修复

1. 只读核对实际表、列、索引与触发器；确认同步客户端 ID 无重复，没有其他活动连接操作目标库，模型别名与优先级列已经存在。
2. 将原有全部 18 张表的结构及 48 行数据备份到 Git 忽略的 `TestResults/startup-repair-backups/`。备份含账户、令牌和密钥数据，只保留在本地，不提交或上传。SQL 备份应恢复到独立空库，不能直接向非空库重复导入。
3. 执行已有 `src/RelaxKon.Auth/Resources/merge/architecture-upgrade.sql`，新增 SyncAccounts、SyncChanges、RoutingConfiguration、2 个聊天唯一索引及 12 个路由触发器。没有重跑 init.sql，没有删除或合并既有数据。
4. 对所有原有表逐行生成 SHA256，排序后汇总比较；迁移前后行数与内容指纹均一致。检查新增结构与路由版本种子行通过。
5. 重新用 http 启动配置运行，成功监听 localhost:5111；Swagger 页面与 JSON、验证码、公开模型接口均返回 HTTP 200。验证结束后停止临时进程，开发者可用 Rider 或原命令正常启动。

此修复只针对当前开发连接对应的数据库，不代表已经升级其他部署环境。

## 代码防回归

新增 ArchitectureSchemaCheck 和 DatabaseSchemaValidationService。启动时先只读检查所需列、唯一索引、路由触发器和版本种子行，再加载路由。缺少结构时明确列出对象与 architecture-upgrade.sql 路径，并提示停止写入、备份和核对部分迁移状态。

常规 Web 启动不会自动执行 DDL，不会绕过迁移继续提供残缺服务，也不会把连接串或密码放进诊断消息。现有数据库连接失败仍按实际连接异常报告。

## 验证

- Release 构建及 137 项常规测试通过。
- 专用隔离 MySQL 测试 12 项通过，包含原有升级、并发同步、路由触发器，以及新增启动检查测试。
- 新测试确认：旧库收到明确迁移提示，检查不创建表或修改聊天记录；升级后通过；新库通过，删除 Id=1 种子行后能明确拒绝启动。
- 当前开发连接的真实启动及 4 个只读/无业务写入 HTTP 接口验证通过。未调用供应商计费接口，也未修改账户、密码或模型配置。

## 其他环境遇到相同问题

参照 [部署指南](deployment.md) 的架构升级步骤。先核对当前连接实际指向的数据库，再备份和检查重复数据。脚本是一次性、非事务 DDL；部分对象已存在时不能整份盲目重跑，应按实际缺失对象恢复。不要将问题替换成 EnsureCreated、自动删库重建或忽略路由加载错误。
