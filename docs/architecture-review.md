## 设计与兼容策略

- 前端：页面 → ChatSessionFacade / SyncService → 类型化协议、SyncLocalStore / DbService。Store 保存快照，流式草稿属于组件作用域的 facade。
- 后端：Controller → ChatService / DataSyncService → 供应商适配器与 EF。旧同步控制器也是应用服务的入口；仓储只保留读取，避免绕过变更日志的第二条写路径。
- SSE 新客户端发送 `Accept: text/event-stream`；只有显式 completed 才算成功。旧客户端未声明此 Accept 时仍收到纯文本，输出后的错误通过断开连接报告。
- 同步服务使用账户行锁保证版本顺序与提交顺序一致；数据、删除事件、幂等操作 ID 一起提交。相同操作 ID 和载荷重试返回原版本；载荷不同返回 409。
- 同一实体采用服务端接收顺序决定最后一次写入，不做字段级合并。消息操作要求先有会话；浏览器将会话与消息操作一起排入队列。
- 第一次拉取是完整快照，后续每批最多 200 条变化。第一次升级会导入本机独有的已登录账户记录；已有服务端 ID 以服务端版本为准。旧协议无法区分“离线未上传”和“曾被其他设备删除”，首次导入可能恢复这类旧记录；升级后的删除使用持久化事件传播。访客数据不自动上传。
- 队列与账户隔离；切换账户停止旧同步；请求携带预期账户头，服务端与认证主体比较，避免令牌刷新期间串号。写入成功但确认丢失时，保留相同操作 ID 重试。
- 多标签页共享队列，服务端幂等处理重复投递；本地事务检查请求开始时的游标和待发送操作，拒绝过期快照，避免覆盖新编辑。
- 变更日志和幂等记录目前不自动清理。首次完整快照和附件日志的容量应纳入部署监控；没有实现有保留期的日志压缩或字段级冲突解决。

## 路由配置失效

`Models`、`SupplierKeys`、`ModelKeyBinds`、`AvailableModels` 的写入触发共享版本递增。各实例默认每 5 秒检测，按一致性事务读取配置，再原子发布快照。手动刷新仍可用，但不再是其他实例感知变化的唯一途径。

`AiRouting:RefreshIntervalSeconds` 可设为 1–60，默认 5；`MaxStaleSeconds` 默认 30、最小 10。刷新单次最多等待 10 秒，数据库命令超时 5 秒。无法确认版本超过失效阈值后清空路由，恢复连接时即使版本未变也重新加载。默认配置下故障检测还受轮询和超时影响，停用旧路由通常在约 45 秒内完成；这约束新请求，不会终止已经开始的上游流。

## 升级与回滚边界

1. 停止写入并备份现有数据库。检查 `(UserId, DataId)` 的历史重复项与 `(ChatHistoryId, DataId)` 的消息重复项，由维护者明确处理，脚本不自动合并或删除。
2. 已有数据库只运行服务端 `src/Turbo.Auth/Resources/merge/architecture-upgrade.sql` 一次；全新数据库使用更新后的 `merge/init.sql`。DDL 需要创建触发器的权限，MySQL DDL 不能事务回滚；中断时先检查已执行的语句。
3. 先部署新后端，再部署新前端并刷新 PWA 资源。新前端不接受旧后端的无完成标记文本流。应用启动会加载路由版本；缺少迁移表时启动失败，不会静默忽略。
4. 浏览器 v4 在升级事务内复制旧会话/消息/标题，保留原存储；队列与同步游标保存在 IndexedDB。不要通过清空站点数据“修复”仍有待同步操作的浏览器。
5. 新后端必须保留为所有写入生成变更日志。直接回退到不生成日志的旧后端会破坏已发出的游标语义；应用回滚需要同时制定客户端游标重置与数据库恢复方案。

## 验证与限制

验证包括：账户/会话重复 ID、消息及附件事务回滚、稳定消息身份、会话取消、冻结状态编辑、UTF-8 分片、未完成/异常流、四家模拟供应商、队列确认丢失、删除传播、账户切换、首次升级保留、本地数据库打开失败、多标签页过期响应、共享路由版本与过期清空。

SQLite 用于本地关系数据库事务测试，浏览器使用真实 IndexedDB。SQLite 不能替代 MySQL 的行锁、触发器和 DDL 联调。初次实现时尚未运行真实 MySQL 集成。后续已通过本地忽略的测试连接，在 MySQL 8.4.13 上完成 10 项架构集成验证，修复 EF 跟踪旧版本值的问题；普通 Release 回归 100 项通过。详细证据及复现命令见后端仓库 `docs/mysql-verification.md`。真实供应商联网调用仍未运行，没有操作生产数据库或部署应用。
